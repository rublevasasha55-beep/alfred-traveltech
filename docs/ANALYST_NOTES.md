# Альфред — пояснения системного аналитика

## Что решает продукт

Наблюдение за статусом рейса само по себе не спасает путешествие. При задержке первый риск — пересадка, далее трансфер, заселение, активность, участники группы. Альфред показывает связанные последствия, отвергает небезопасные варианты и предлагает «План Б».

## В MVP реализовано

- Ввод демонстрационного события `delayed` / `cancelled` / `on_time`.
- Сравнение `event_id` (идемпотентность) и `observed_at` (защита от устаревших данных).
- Расчёт пересадки в UTC с локальным отображением.
- Отбрасывание авиавариантов по багажу, транзитным документам и времени пересадки.
- Согласование варианта пользователем и обновление **черновика** общего плана (без реальной переброни).
- Очередь уведомлений, когда пользователь помечен офлайн, и синхронизация при возврате онлайн.
- Локальный FastAPI для воспроизведения контрактов событий и получения состояния.

## Что нужно в промышленной версии

- Реальные договоры и интеграции с поставщиками рейсов / OTA / почтой с разрешениями.
- Раздельные `observed_at` (время факта у источника), `received_at` (время приёма), `effective_at` (действие статуса).
- Надёжная очередь, event store, репликация, SLA/SLI и алертинг.
- Отдельный сервис проверок визовых/транзитных правил с актуальными источниками; неизвестная виза → требуется ручная проверка.
- Свежесть стоимости / остатков мест, подтверждение правил багажа и возвратов. Отсутствие подтверждения ≠ бронирование.
- Двухфазный сценарий изменения: согласие пользователя → резервирование → подтверждение поставщика → обновление общего плана; компенсация при частичном отказе.
- Групповые согласования и конфликты параллельных правок (optimistic locking с `revision`).
- Уведомления push/email/SMS с согласиями, TTL, ретраями и офлайн-получением.
- Контроль доступа, шифрование, логирование без персональных данных, минимальный срок хранения паспортных данных: только пока они нужны по цели и закону; автоматическое удаление, подтверждаемое аудитом.

## Критерии приёмки (предлагаемые, требуют согласования)

1. Повтор `event_id` не создаёт второй инцидент или уведомление.
2. Более старый `observed_at` не заменяет более свежий статус.
3. После задержки +120 мин первая пересадка даёт 20 мин, считается критичной.
4. Вариант без требуемого багажа или с неизвестными транзитными документами не допускается к выбору.
5. Уведомление, сформированное офлайн, сохраняется до синхронизации.
6. Без согласия пользователя нельзя выполнять покупку/отмену билетов.
7. Конфликт обновления группового маршрута не теряет чужие изменения.

## Граница безопасности и приватности

В демо нет паспортов и реальных бронирований. Визовые флаги — условные признаки. Локальный API не содержит production-аутентификации и должен работать только на `127.0.0.1`.
